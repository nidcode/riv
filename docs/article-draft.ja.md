# re:Invent のアジェンダを「コード」で管理する riv を作った

re:Invent の予定を Markdown に書いて、差分を見てから反映するツール、riv を作りました。取れた席を失わずに予定を組み替えられることを一番の目的にしています。

リポジトリ: https://github.com/nidcode/riv

## 作った理由

セッションは2,000件を超えます。毎日の予定は、行きたい話を探す、重なりに気づく、組み替える、の繰り返しになります。ここで一番怖いのは、取れている席を自分の操作で失うことです。席は一度手放すと戻らないことがあります。

AI アシスタントに任せる手もありますが、カタログ全体がチャットに流れ込むのは避けたいと思いました。API には検索機能がないので、全件を取って手元で絞る必要があります。

## 仕組み

- カタログは手元の SQLite に保存します。AI には検索結果の数行だけを返します。
- 欲しい予定は `design.md` の末尾に YAML で書きます。`reserved`、`favorite`、`none` から選びます。
- `riv plan` が、実際のスケジュールとの差分を表示します。この時点では何も書き込みません。
- `riv apply --plan <ID>` が、その差分だけを実行します。

守っていることは次のとおりです。

- 自分で作っていない予約には触りません。YAML の行を消しても取り消しません。取り消すときは `want: none` と書きます。
- 予約の置換は、先に取り消してから取るので、席を失う可能性があります。差分に明記し、フラグを付けないと適用できません。
- タイムアウトなどで結果が分からないときは、再送せずに止まります。`--resume` でスケジュールを読み直し、足りない分だけ送ります。API に冪等性キーがないためです。
- 席を自動で取りに行く機能はありません。

## API と MCP の使い方

REST の12操作はすべて実装しました。予約、取消、お気に入り、個人時間の作成・更新・削除もあります。個人時間の作成・更新・削除は、実 API では試せていません。モックサーバーでテストしました。

リモート MCP サーバーは、REST との比較に使いました。ローカル用には自作の MCP サーバーを用意しています（`riv_search`、`riv_plan`、`riv_apply` など9ツール）。返す内容は小さくしてあり、`riv_apply` は人が承認したときだけ動かす前提です。

Kiro では Power として入れられ、Kiro Crew に登録すればスマホからも使えます。

## 測ってみた

実際のカタログ（2,195件）で計りました。

| 項目 | 結果 |
|---|---|
| 初回の全件同期 | 約13秒（概要あり・なしとも） |
| 手元の検索（50回） | 中央値0.6ms、95%点1.8ms |
| 1ページ取得（REST） | 中央値1.34秒、317KB |
| 1ページ取得（リモート MCP） | 中央値1.64秒、317KB |

1ページあたりのサイズは、REST でも MCP でも同じでした。MCP 経由で AI に全件を読ませるなら、この大きさのページを何十回も通すことになります。手元に置いて検索すれば、AI に渡るのは数行です。時間は5回の測定で、MCP の方が0.3秒ほど遅くなりました。

## 使ってみて

自分の予定を作ってみました。興味のあるテーマで絞り、お気に入りを7件入れたところで、GameDay（3時間）が他のセッションと重なっていることに気づきました。重なりは一覧では見落としがちですが、差分の段階で分かりました。

10月8日の時点では、API からの予約は 409 で閉じていました。公式サイトでは先に開いています。そのため、予約は手動で取りました。API 側は、開いたら `riv plan` と `riv apply` で足りない分だけ入れます。

## できていないこと

- セッションコードを年をまたいで対応づける処理は、推測です。
- 会場間の移動時間は、自分で設定ファイルに書く必要があります。値は用意していません。
- 日本語の検索は、形態素解析をしていないので精度が高くありません。
- 一部の GameDay は、予約の対象外のようです。
